# Quickstart: Проверка резервной стратегии применения правил брандмауэра

## Предпосылки

- Решение собирается без ошибок: `dotnet build src/Steamoff.sln -c Debug` (или весь `.sln`, в зависимости от того, что используется в репозитории).
- Юнит-тесты проходят: `dotnet test tests/Steamoff.Tests/Steamoff.Tests.csproj` (без категории `RequiresAdmin`).
- Приложение запускается с правами администратора (как и раньше — элевация не меняется этой фичей).

## Сценарий A — "Счастливый путь": основная стратегия работает (большинство машин)

Цель: подтвердить, что при исправно работающем COM-пути поведение НЕ изменилось — резерв не запускается, журнал не стал многословнее (FR-010, Принцип VI).

1. На машине, где `ComFirewallService` создаёт правила штатно (без стороннего ПО, перехватывающего COM-автоматизацию), включить переключатель блокировки Steam.
2. Проверить `steamoff.log`: должна появиться обычная последовательность `FirewallBlockStarted` → … → `FirewallBlockCompleted`, БЕЗ записей `FirewallStrategyFallbackUsed`/`FirewallBothStrategiesFailed`.
3. Проверить правила группы `Steamoff` через `netsh advfirewall firewall show rule name=all | findstr /I "Steamoff"` (или `Get-NetFirewallRule -Group Steamoff` из обычного, неэлевированного PowerShell для просмотра) — правила присутствуют и именованы по схеме `Steamoff - Block - <Цель> - <Направление>`.
4. Проверить локализованный пользовательский журнал в UI приложения — резюме операции не упоминает "резерв"/"fallback"/смену стратегии (соответствует поведению ДО этой фичи).

**Ожидаемый результат**: Поведение и журналы идентичны состоянию до внедрения фичи — нулевые накладные расходы на счастливом пути.

## Сценарий B — Основная стратегия не срабатывает → автоматический резерв (целевой сценарий пользователя)

Цель: воспроизвести и подтвердить исправление исходной проблемы — на машине пользователя (где COM-путь молча проваливается с `FileNotFoundException (0x80070002)`, как зафиксировано в `steamoff.log` ранее в этой сессии) включение блокировки теперь действительно создаёт правила через резервную стратегию.

1. На затронутой машине (COMODO Internet Security активен, `cis.exe`/`cmdagent.exe` запущены) включить переключатель блокировки Steam.
2. Проверить `steamoff.log`:
   - Запись о провале основной стратегии (исключение `FileNotFoundException`/предупреждения по каждой цели — уже существующее поведение per-target try/catch).
   - Новая запись `FirewallStrategyFallbackUsed` с указанием причины (`Exception` или `NoRulesProduced`) и итоговой статистики (сколько целей обработал резерв).
   - Финальная `FirewallBlockCompleted`.
3. Проверить локализованный пользовательский журнал — присутствует понятное краткое резюме о том, что использован резервный механизм (текст на языке интерфейса пользователя, см. `log.event.firewallStrategyFallbackUsed`).
4. Проверить правила группы `Steamoff` (`netsh advfirewall firewall show rule name=all | findstr /I "Steamoff"`): правила присутствуют, именованы по той же схеме `Steamoff - Block - <Цель> - <Направление>`, что и в Сценарии A — никакой "SteamOfflineToggle"/"Steam Offline IN/OUT" конвенции.
5. Запустить Steam и убедиться, что сетевой доступ у клиента и связанных процессов действительно заблокирован (тот же критерий приёмки, что и для исходной фичи блокировки).

**Ожидаемый результат**: SC-001 — на затронутой машине правила создаются в 100% случаев (через резерв), пользователь однозначно понимает (SC-003), что сработал резервный путь, и почему.

## Сценарий C — Обе стратегии не справились

Цель: подтвердить единое, понятное сообщение об ошибке вместо тишины или противоречивых сообщений (FR-008, SC-004).

1. Гипотетически смоделировать (например, временно остановив службу `MpsSvc`/Windows Defender Firewall, если это допустимо в тестовой среде, либо через фейковые реализации в юнит-тестах — см. ниже) ситуацию, когда ни COM, ни `New-NetFirewallRule` не могут создать правила.
2. Проверить, что в обоих журналах (техническом и пользовательском) присутствует ОДНО ясное сообщение `FirewallBothStrategiesFailed` — без молчаливого "операция завершена" и без двух противоречащих друг другу предупреждений.

**Ожидаемый результат**: пользователь в течение нескольких секунд понимает из интерфейса, что блокировка не удалась и почему — соответствует SC-004.

## Юнит-тестовая проверка (без реального брандмауэра)

`tests/Steamoff.Tests/Infrastructure/FallbackAwareFirewallServiceTests.cs` — три ключевых случая на фейковых `IFirewallService`-стратегиях:

```csharp
// 1. Primary succeeds & verification shows expected rules → Fallback never invoked, no "strategy" log entries
// 2. Primary throws → Fallback invoked, FirewallStrategyFallbackUsed logged with FailureReason.Exception
// 3. Primary "succeeds" but verification shows zero rules → Fallback invoked, FailureReason.NoRulesProduced
// 4. Both fail → FirewallBothStrategiesFailed logged once, clear exception surfaced to caller
```

Запуск: `dotnet test tests/Steamoff.Tests/Steamoff.Tests.csproj --filter FullyQualifiedName~FallbackAwareFirewallServiceTests`

Реальная проверка `NetSecurityFirewallService` против живого брандмауэра — отдельный `RequiresAdmin`-тест, по умолчанию пропускаемый (как и существующие admin-тесты в проекте); запускается только вручную на элевированной машине и обязан подчищать за собой созданные правила.
