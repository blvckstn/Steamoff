# Data Model: Резервная стратегия применения правил брандмауэра

Эта фича не вводит новых персистентных сущностей (ничего не сохраняется на диск сверх уже существующего лога/журнала). Ниже — модели времени выполнения, нужные для оркестрации и логирования; они напрямую реализуют ключевые сущности, описанные в spec.md ("Стратегия применения правил" и "Запись о выполненной операции").

## FirewallStrategyKind (enum)

Идентифицирует, какая реализация `IFirewallService` фактически выполнила работу. Используется и в логах (как структурированный аргумент `LogAsync`), и внутри оркестратора для принятия решений.

| Значение | Описание |
|---|---|
| `Primary` | Основная стратегия — `ComFirewallService` (`INetFwPolicy2`/COM-автоматизация) |
| `Fallback` | Резервная стратегия — `NetSecurityFirewallService` (`New-NetFirewallRule`/PowerShell `NetSecurity`) |

Соответствует "Стратегии применения правил" из спецификации: ровно два варианта, порядок применения фиксирован (`Primary`, затем при необходимости `Fallback`), расширения сверх двух не предполагаются (YAGNI — текущая спецификация и конституция называют только эти два документированных пути).

## StrategyFailureReason (enum)

Почему оркестратор счёл основную стратегию неуспешной — пишется в технический лог при переключении на резерв (FR-006), помогает будущей диагностике отличить "поймали исключение" от "тихо ничего не создалось".

| Значение | Описание |
|---|---|
| `Exception` | Основная стратегия выбросила необработанное исключение во время операции |
| `NoRulesProduced` | Операция завершилась без исключения, но верификация (`GetCurrentStateAsync`) показала, что ожидавшиеся правила группы `Steamoff` фактически не появились/не изменились |

## RuleApplicationOutcome (внутренняя запись результата операции)

Возвращаемое (внутреннее, не публичное в `IFirewallService`) представление того, что именно произошло за один вызов `ApplyBlockAsync`/`RemoveOrDisableAsync` — соответствует "Записи о выполненной операции применения правил" из спецификации. Используется оркестратором, чтобы решить, нужен ли резерв, и что именно записать в оба журнала.

| Поле | Тип | Назначение |
|---|---|---|
| `StrategyUsed` | `FirewallStrategyKind` | Какая стратегия в итоге выполнила операцию (та, чей результат был принят как окончательный) |
| `FellBackFromPrimary` | `bool` | Произошло ли переключение на резерв в рамках этого вызова |
| `FailureReason` | `StrategyFailureReason?` | Заполняется только когда `FellBackFromPrimary == true`; объясняет, почему основная стратегия была признана неуспешной |
| `AffectedTargetCount` | `int` | Сколько целей было фактически обработано выбранной стратегией — для содержательного резюме в логах |

Это — структура для внутреннего использования внутри `FallbackAwareFirewallService` (не часть публичного контракта `IFirewallService`, не сериализуется и не персистится); при необходимости тестов фейковые стратегии могут возвращать предсказуемые `RuleApplicationOutcome`-подобные сигналы через свои публичные побочные эффекты (что вызвано, что выброшено), а не напрямую через эту структуру.

## Связь с существующими моделями (без изменений)

- **`FirewallTarget`** (`Steamoff.Core.Models.TargetModels`) — список целей передаётся обеим стратегиям без изменений; ни одна стратегия не модифицирует и не порождает новых типов целей.
- **`FirewallConstants`** (`RuleGroup = "Steamoff"`, `RuleNamePrefix = "Steamoff - Block - "`) и **`FirewallRuleNameBuilder.Build(displayName, direction)`** — единственный источник истины для имён и группы правил; обе стратегии (и `ComFirewallService`, и новый `NetSecurityFirewallService`) обязаны строить имена правил исключительно через них, что напрямую реализует FR-004/FR-005 и Принцип II конституции ("Rules without this signature belong to someone else").
- **`ActualFirewallState` / `FirewallRuleState`** — возвращаются из `GetCurrentStateAsync()` обеими стратегиями в одинаковом формате; именно на их основе оркестратор выполняет верификацию "создалось ли вообще что-то" (R2 из research.md).
- **`LogEventKey`/`LogEventTemplates`** — расширяются двумя новыми значениями (`FirewallStrategyFallbackUsed`, `FirewallBothStrategiesFailed`), см. research.md R4; формат записи (`LogAsync(key, params object[] args)`) не меняется.

## Состояния и переходы (по одному вызову `ApplyBlockAsync`/`RemoveOrDisableAsync`)

```text
[Старт операции]
      │
      ▼
Выполнить через Primary (ComFirewallService)
      │
      ├─ Исключение всей операции? ───────────────┐
      │                                            │
      ▼ нет                                        ▼ да
Верифицировать состояние (GetCurrentStateAsync)   FailureReason = Exception
      │                                            │
      ├─ Ожидаемые правила появились? ─────┐       │
      │                                     │       │
      ▼ да                                  ▼ нет   │
StrategyUsed = Primary                FailureReason = NoRulesProduced
FellBackFromPrimary = false                 │       │
→ лог: обычное событие                      └───┬───┘
  (FirewallBlockCompleted/                       ▼
   FirewallUnblockCompleted),                Выполнить через Fallback (NetSecurityFirewallService)
  без упоминания стратегии                       │
                                                  ├─ Тоже неуспех (исключение ИЛИ верификация пуста)?
                                                  │
                                          да ◄────┴────► нет
                                          │                │
                                          ▼                ▼
                                StrategyUsed = Fallback   StrategyUsed = Fallback
                                FellBackFromPrimary=true  FellBackFromPrimary = true
                                → лог:                    → лог:
                                  FirewallBothStrategiesFailed   FirewallStrategyFallbackUsed
                                  (единое понятное               (+ FailureReason, + обычное
                                   сообщение об ошибке,           событие завершения операции)
                                   FR-008)
```

Замечание: устойчивость "один таргет не должен ронять всю операцию" (FR-009) реализуется ВНУТРИ каждой стратегии (как уже сделано в `ComFirewallService.ApplyBlockAsync` через per-target try/catch, и должно быть зеркально повторено в `NetSecurityFirewallService`) — оркестратор оперирует только на уровне "операция в целом дала ожидаемый результат или нет", не вмешиваясь в по-таргетную логику каждой стратегии.
