# Quickstart: проверка ScriptFile-стратегии, режима выбора и самотестирования

Этот гайд описывает, как воспроизводимо убедиться, что фича работает end-to-end — без полных тел реализации
(они в tasks.md/коде). Соответствует трём независимым пользовательским историям из spec.md.

## Предусловия

- Решение собирается и существующий набор тестов зелёный (124/124 на момент начала фичи — контрольная точка "не
  сломал ничего из 006"): `dotnet test` из корня репозитория.
- Для сценариев, требующих реального elevated-процесса/живого брандмауэра — Windows-машина с правами
  администратора; такие тесты помечены категорией `RequiresAdmin` и по умолчанию пропускаются
  (`dotnet test --filter "Category!=RequiresAdmin"` — текущий CI-режим).

## US1 — Третья стратегия работает изолированно ("Вариант 3" форсирован)

1. В Settings выбрать "Вариант 3".
2. Включить блокировку Steam ("Block Steam").
3. **Ожидаемо**: в `Get-NetFirewallRule -Group "Steamoff"` появляются правила с именами вида
   `"Steamoff - Block - <Target> - Outbound"` (через `FirewallRuleNameBuilder` — идентично "Вариант 1"/"Вариант 2"),
   включены, блокируют исходящий трафик целевых `.exe`. Технический лог отмечает, что использован "Вариант 3"
   (без упоминания резерва — это форсированный режим, не каскад).
4. Выключить блокировку ("Unblock Steam").
5. **Ожидаемо**: правила удалены/выключены согласно `RuleCleanupMode`, доступ восстановлен.
6. Повторить шаги 2-5 несколько раз подряд через несколько запусков приложения.
7. **Ожидаемо**: на диске остаётся РОВНО ОДИН файл `Scripts\steamoff-firewall.ps1` рядом с исполняемым файлом —
   не накапливаются временные/конфликтующие копии (FR-005).

Юнит-проверка без реального процесса: `ScriptFileFirewallServiceTests` со scripted `IPowerShellCommandRunner`
double — подтверждает корректные `STEAMOFF_*` переменные окружения, аргументы запуска (`-File`, без `runas`),
per-target резильентность и идентичность именования правил (зеркало `NetSecurityFirewallServiceTests`, если
существуют, иначе — паттерн `FallbackAwareFirewallServiceTests`/`ScriptedFirewallService`).

## US2 — Выбор и доверие к конкретной стратегии через Settings

1. Открыть Settings → увидеть четыре варианта: "Авто"/"Вариант 1"/"Вариант 2"/"Вариант 3" с пояснениями и
   текущим выбором (FR-007).
2. Выбрать "Вариант 2", вызвать сбой этой стратегии (например, временно лишить её прав через тестовый double —
   в реальности: машина, где она в принципе не работает) и включить блокировку.
3. **Ожидаемо**: явное сообщение об ОТКАЗЕ именно "Варианта 2" в обоих журналах, БЕЗ автоматической попытки
   "Варианта 1"/"Варианта 3" (FR-008) — новое событие `FirewallForcedStrategyFailed`.
4. Переключить на "Авто". Добиться успешного выполнения через "Вариант 3" (например, единственный рабочий на
   данной машине).
5. Повторить операцию в режиме "Авто".
6. **Ожидаемо**: оркестратор пробует "Вариант 3" ПЕРВЫМ (запомненный последний успех — FR-009), не начиная
   каскад заново с "Варианта 1".
7. Сменить режим в Settings прямо во время выполнения операции (если возможно симулировать через искусственную
   задержку в тестовом double).
8. **Ожидаемо**: уже идущая операция завершается с режимом, который был активен на момент её старта; новый режим
   применяется только к следующей операции (FR-014).

Юнит-проверка: расширенные `FallbackAwareFirewallServiceTests` — `ApplyBlockAsync_ForcedMode_*`,
`ApplyBlockAsync_AutoMode_TriesRememberedStrategyFirst`, `ApplyBlockAsync_AutoMode_AllThreeFail_LogsAndThrows`,
`ApplyBlockAsync_ModeCapturedAtOperationStart_NotMidOperation`.

## US3 — Первичное самотестирование на самом первом запуске

1. Сбросить локальное состояние приложения до "никогда не запускалось" (удалить/переименовать файл настроек —
   эквивалент свежей установки; см. `FirewallSelfTest.Outcome = NotYetRun`).
2. Запустить приложение.
3. **Ожидаемо**: автоматически и БЕЗ какого-либо видимого взаимодействия запускается проверка всех трёх стратегий
   (FR-010); занимает доли секунды — никакого UI-блокирования, никакого предупреждения/диалога.
4. Сразу после запуска проверить набор ИМЁН правил группы `"Steamoff"` ДО и ПОСЛЕ (не сам факт временного
   присутствия зонда — см. примечание ниже).
5. **Ожидаемо**: набор реальных Steamoff-целей идентичен (никаких новых/изменённых/удалённых записей для уже
   управляемых целей) — проверочное правило было немедленно удалено и не пересекается по имени ни с одной
   реальной целью (FR-011, SC-004).
   > **Адаптация реализации**: контракт C5 предписывал отдельную группу брандмауэра `"Steamoff-SelfTest-Probe"`,
   > но все три `IFirewallService` (включая ScriptFile) жёстко используют `FirewallConstants.RuleGroup` и
   > игнорируют `FirewallTarget.GroupName` — менять их запрещено ("Strategies 1 and 2 must remain functionally
   > unchanged"). Изоляция вместо этого достигается уникальным sentinel-именем цели
   > `DisplayName = "Steamoff-SelfTest-Probe"`: `FirewallRuleNameBuilder` превращает его в имя правила, которое
   > никакая реальная цель произвести не может, оно никогда не учитывается в подсчёте покрытия и гарантированно
   > удаляется в `try/finally` (см. XML-документацию `FirewallSelfTestRunner`).
6. Открыть лог.
7. **Ожидаемо**: одна чёткая запись — какие варианты сработали/не сработали, понятная нетехническому пользователю
   (FR-012, новое `LogEventKey.FirewallSelfTestCompleted`).
8. Выполнить первую реальную операцию блокировки в режиме "Авто".
9. **Ожидаемо**: оркестратор сразу пробует вариант, который самотест нашёл рабочим — без "обучения через провал"
   (FR-010, US3 Acceptance Scenario 3, SC-003).
10. Перезапустить приложение несколько раз.
11. **Ожидаемо**: самотест НЕ повторяется (`Outcome` остаётся `CompletedWithResult`/`Inconclusive` — FR-013).

Юнит-проверка: `FirewallSelfTestRunnerTests` — `RunIfNeededAsync_FirstRun_ProbesAllThreeAndSeedsLastSuccess`,
`RunIfNeededAsync_AlreadyRun_IsNoOp`, `RunIfNeededAsync_ProbeRulesAlwaysCleanedUp_EvenOnFailure`,
`RunIfNeededAsync_Interrupted_RecordsInconclusiveDistinctFromNotYetRun`.

## Контрольная точка "ничего не сломано" (FR-015 / SC-006)

Запустить полный набор тестов (`dotnet test --filter "Category!=RequiresAdmin"`) и убедиться, что:
- предыдущие 124 теста по-прежнему зелёные;
- пользователь, никогда не открывавший новую настройку (т.е. с `FirewallStrategyMode = Auto` и пустой памятью),
  наблюдает поведение, неотличимое от двухстороннего каскада feature 006, кроме как в моменты, когда самотест/
  реальный успех уже заполнили память — и даже тогда наблюдаемый эффект является строгим уточнением
  ("пробуем сначала то, что уже работало"), а не изменением контракта.
